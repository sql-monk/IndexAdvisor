# QUESTIONS.md — неоднозначності ТЗ і прийняті тлумачення

Формат: **Питання** — розділ ТЗ — прийняте (найбезпечніше) тлумачення. Потоки дописують у свій розділ.

## Оркестратор (контракти)

1. **Параметри «передаються драйверу як позиційні»** (4.7). Microsoft.Data.SqlClient працює з іменованими параметрами. Прийнято: у тексті лише `@Name`, значення передаються як `SqlParameter`, склеювання заборонене, невідомий чи відсутній параметр — помилка.
2. **Маскування літералів: обов'язкове чи опційне?** (4.3.1 — «очищуються», розділ 6 — «опційна»). Прийнято: літерали в текстах запитів очищуються завжди; опційне лише маскування імен (`llm.maskNames`).
3. **Пом'якшений мінімальний період проти «мінімум 14 днів»** (4.4). Прийнято: стандартний `rules.drop.minUptimeDays` ≥ 14; пом'якшений `rules.relaxed.minUptimeDays` окремий (за замовчуванням 7), застосовується лише до «дорогих» індексів.
4. **Дедлоки з sys.dm_db_index_operational_stats** (4.4). У DMV немає лічильника дедлоків. Прийнято: «дорогий» індекс визначається за lock/latch-очікуваннями й співвідношенням записів до читань; дедлоки не рахуються.
5. **«Не підтримує FK»** (4.4, 4.8). Прийнято: блокують видалення обидва випадки — унікальний індекс, на який посилається FK (`referencedByForeignKeys`), і індекс, що покриває колонки FK дочірньої таблиці (`coversForeignKeys`).
6. **«Початок місяця»** (4.4). Прийнято: перші `analysisWindow.monthStartDays` днів (за замовчуванням 5).
7. **Час failover і rebuild** (4.3). Прямого DMV немає. Прийнято: колектор визначає за можливості (AlwaysOn_health через системні функції, лише SELECT), інакше `null` з попередженням; період рахується від запуску інстансу.
8. **Мапа маскування в архіві**. Прийнято: мапа зберігається поруч із ZIP (`.map.json`), не всередині, щоб маскований архів можна було передати без мапи.
9. **ApplicationIntent для вторинних реплік** (4.7). За замовчуванням не задається; для вторинної з `ALLOW_CONNECTIONS = READ_ONLY` без `ApplicationIntent=ReadOnly` прямий доступ до бази неможливий. Прийнято: `ReadOnly` задається лише в цьому випадку, репліки з `NO` пропускаються з попередженням.
10. **SQL-скрипт видалення, умови 4.4 якого не виконано**. Прийнято: файл містить закоментовані інструкції й пояснення, щоб його не можна було виконати випадково; у MD/HTML скрипт показаний повністю з попередженням.
11. **«Метод» у Markdown-інструменті** (4.7). Прийнято: єдине допустиме значення `Query` (read-only SELECT).
12. **Рекомендація «залишити» з аналізу з коротким періодом**. Прийнято: будь-який вердикт `Keep` обнуляє серію (консервативно щодо видалення).
13. **Генерація пароля** (розділ 6). T-SQL не має доступу до SecretManagement. Прийнято: пароль генерує обгортка PowerShell, одразу зберігає у сховищі й передає скрипту через sqlcmd-змінну; сам T-SQL-скрипт пароль не генерує й не виводить.
14. **Вимкнення таймауту** (4.7). Прийнято: `unsafe.disableTimeouts` вимикає лише таймаут виконання команди; `LOCK_TIMEOUT` і таймаут підключення лишаються.
15. **Список серверів**. Прийнято: кожен сервер — окремий запуск (окремий snapshot, архів, RunResult, запис у репозиторії).
16. **Злиття індексів**. Прийнято: злиття = рекомендація CreateIndex (з `replacesIndexes`) + окремі DropIndex для зайвих індексів, кожна з яких проходить правила 4.4.
17. **Критичні рекомендації для cross-check** (розділ 5). Прийнято: DropIndex і будь-яка з `risk.level = High`.
18. **Перевірка джерел при вимкненій перевірці SELECT**. Прийнято: обмеження «лише системні каталоги, DMV і Query Store» не входить до переліку вимикних і діє завжди.
19. **Регулярний запуск за розкладом** (4.1). Прийнято: окремого планувальника немає; підтримується неінтерактивний режим з кодами повернення, приклади розкладу — у README.
20. **Query Store на вторинних репліках**. У SQL Server 2019 дані Query Store вторинної репліки — копія primary. Прийнято: Query Store читається з primary, для вторинних — попередження.
21. **«Жоден план у Query Store за весь період спостереження»** (4.3.1). Прийнято (під час інтеграції): плани для `queryStoreUsage` і умови `NotUsedInQueryStore` скануються за весь період, що зберігає Query Store, а не лише у вікні аналізу; топ-запити й профілі за годинами — у вікні.
22. **Попередження про великий обсяг рядків** (4.7). Прийнято (під час інтеграції): попередження про контекст і вартість токенів виводиться лише для дозапитів моделі (`Purpose Tool/FreeQuery`); колектор читає сторінками по `limits.maxRows`, і ці дані не йдуть у модель напряму.
23. **Розташування JSON-схем**. Прийнято (під час інтеграції): `contracts/` перенесено всередину модуля (`src/IndexAdvisor/contracts/`), бо схема відповіді моделі потрібна під час виконання.
24. **Довжина ключа `ObjectKey` у репозиторії** (відкрите). Живий прогін скрипта репозиторію на SQL Server 2025 дає попередження: `ObjectKey NVARCHAR(850)` у кластерному PK `(RunId, ObjectKey)` перевищує ліміт 900 байт, а в некластерних індексах — ліміт 1700 байт. Вставка впаде лише для ключа довшого за ~440 символів (типові ключі — 60–150 символів). Варіант виправлення — окремий стовпець-хеш ключа (`HASHBYTES('SHA2_256', ...)`) у PK та індексах; це зміна розділу 8 контрактів, тому відкладено до рішення.

## Потік 1 — Core

1. **Що дозволяє `unsafe.disableSelectCheck`** (4.7, 10). Вимкнення перевірки не може дозволити змін у цільовій базі. Прийнято: вимикається лише вимога «рівно одна SELECT»; запобіжник лишається — один батч (без GO), лише інструкції читання (SELECT без INTO, DECLARE, SET @змінна), перевірка джерел діє завжди; DDL, DML, EXEC, SET-опції, BEGIN TRAN тощо блокуються й тоді.
2. **Purpose `FreeQuery` без `unsafe.allowFreeQuery`**. Прийнято: `Invoke-IaSqlQuery` додатково відхиляє такий виклик (`ArgumentInvalid`) незалежно від того, чи потік Tools завантажив `free_query`.
3. **Штатний логін у конвеєрі**. Прийнято: окрім `Assert-IaStandardLogin` у CLI, `Invoke-IaSqlQuery` перед підключенням сам перевіряє політику (без журналу) і повертає конверт `LoginRefused`, не підключаючись.
4. **Ліміт рядків для UNION/EXCEPT/INTERSECT і особливих TOP**. Прийнято: без ORDER BY такий запит обмежує лише драйвер (читає ≤ Fetch + 1 рядків і скасовує решту); з ORDER BY — `OFFSET 0 ROWS FETCH NEXT`; Skip для них без ORDER BY, Skip разом із TOP чи наявним OFFSET — `ArgumentInvalid`; `TOP (@n)` і `TOP … PERCENT` не змінюються (обмежує драйвер).
5. **Модифікація тексту запиту**. Прийнято: AST ScriptDom + генератор тієї ж версії, що й парсер (Sql170ScriptGenerator); коментарі й форматування не зберігаються; змінений текст перевіряється повторно; у журнал пишеться саме виконуваний текст.
6. **XML-методи у перевірці джерел**. `alias.col.value()` синтаксично не відрізняється від `схема.функція()`. Прийнято: дозволено методи `value`, `query`, `exist`, `nodes`; решта викликів зі схемою — лише `sys.*`. Об'єкти без схеми (крім CTE), `#t`, `@t`, зв'язані сервери — заборонені.
7. **Відсутній секрет пароля в `Invoke-IaSqlQuery`**. Прийнято: конвеєр не кидає винятків — конверт `ConnectionFailed` з поясненням; сам `New-IaConnectionString` кидає `IaConfigInvalid` / `IaSecretNotFound`.
8. **«Зайві» права** (розділ 6). Прийнято: зайвим вважається все, що не входить до прав ролей скрипта підготовки (і неявних з них у SQL Server 2022) та стандартних прав `public` — зокрема фіксовані серверні ролі й ролі бази з доступом до даних, будь-які права на рівні сервера/бази понад читання метаданих (навіть SHOWPLAN), а також GRANT на схеми й користувацькі об'єкти (зокрема через `public`).
9. **Маскування за іменем**. Шаблон `key` збігається і з нейтральними іменами (`keyColumns`, `maxTokensPerAnalysis`). Прийнято: надлишкове маскування безпечніше; додатково маскуються `Password=`/`Pwd=` у будь-якому тексті.
10. **Попередження про обсяг для колектора**. Колектор, що читає сторінками з `Fetch = limits.maxRows`, отримуватиме попередження про обсяг контексту на кожній сторінці (контракт 3.1.1, крок 2). Прийнято: поведінка за контрактом; колектор за потреби викликає з `-WarningAction SilentlyContinue` (повідомлення лишаються в `messages`).
11. **Журнал**. Прийнято: імена файлів журналу — з часом UTC; Write-Warning про unsafe-прапорці на старті робить CLI (крок 2 розділу 4 контрактів), `Start-IaSession` пише їх у журнал з рівнем Warning; каталог журналів не обмежується NTFS (ТЗ вимагає цього лише для архівів), хоча журнал містить повні тексти запитів.

## Потік 2 — Collector

1. **Категорія навантаження ETL/SSIS** (4.3.1). Application Name сесії (SSIS) у Query Store не зберігається. Прийнято: евристика `Get-IaColWorkloadCategory` — `Etl` для INSERT BULK, MERGE, SELECT INTO, DML з avg logical reads ≥ 10 000 або модуля з іменем etl/load/import/export/stag/stg/ssis/extract/transform; `Report` — модуль rpt/report/dashboard/analytic або агрегати (GROUP BY, OVER, SUM…) з avg reads ≥ 10 000; `AdHoc` — непараметризований запит поза модулем з ≤ 10 виконаннями; `Oltp` — легкий параметризований/модульний або ≥ 100 виконань; інакше `Unknown`.
2. **usedByReplication** (4.4). Лише `sys.*`: `sys.databases` (is_published, is_merge_published, is_subscribed) і `sys.tables` (is_replicated, is_merge_published, is_sync_tran_subscribed). Прийнято: на реплікованій таблиці — PK (потрібен транзакційній реплікації) і унікальний індекс із ROWGUIDCOL (merge); у базі-підписнику — будь-який PK або UNIQUE (агент розповсюдження застосовує зміни за ключем). Інші індекси — `false`; набір не зібрано — `null`.
3. **Час останнього failover** (4.3). Прийнято: `sys.fn_xe_file_target_read_file('AlwaysOn_health*.xel')`, подія `availability_replica_state_change`, остання зміна ролі (PRIMARY/SECONDARY) — лише для топології AG; помилка — `null` і попередження `LastFailoverUnknown`. Відсутність подій у збережених файлах XE трактується як «failover не зафіксовано» (`null`).
4. **lastRebuildUtc**. SELECT-ом із системних джерел час останнього rebuild надійно не визначається (STATS_DATE змінюється й при оновленні статистики). Прийнято: завжди `null`.
5. **Вторинні репліки AG**. Прийнято: Query Store не читається (попередження `QueryStoreOnPrimaryOnly`), `sys.dm_db_index_physical_stats` не виконується (фізична структура однакова; `physical.skipped` з причиною), решта наборів (usage, operational, partition_stats, missing index, обмеження) збирається. Репліку з роллю UNKNOWN (топологію бачили з вторинної) підключаємо до master, роль уточнюємо за `sys.databases`/`sys.dm_hadr_availability_replica_states`.
6. **Системні бази**. Прийнято: виключаються master, model, msdb, tempdb, distribution (`is_distributor = 1`) і знімки баз; бази не ONLINE і без доступу (`HAS_DBACCESS = 0`) пропускаються з попередженням.
7. **Шаблони scope для таблиць**. Прийнято: шаблон із крапкою зіставляється з `schema.table`, без крапки — з іменем таблиці; підтримуються лише `*` і `?` (`[` і `]` — звичайні символи); без урахування регістру; exclude має пріоритет над include.
8. **Розмір сторінки для планів і текстів**. Контракт: Fetch = `limits.maxRows`. Прийнято: для запитів із великими текстовими колонками (XML планів, sys.sql_modules, тексти Query Store) сторінка менша — 100/200/500 рядків (не більше maxRows), щоб не тримати в пам'яті тисячі XML; XML повертається лише для першого плану кожного query_plan_hash, розбір кешується.
9. **index.queryStoreUsage** (4.3.1, 4.4). Прийнято: рахуються лише читання (Seek, Scan, Lookup) з усіх планів, виконаних у вікні аналізу (не лише топ-запитів), зокрема міжбазові посилання в межах інстансу; оновлення індексу DML-планом використанням не вважається. Невалідний XML — запасний пошук посилань регулярним виразом (використання враховується без типу операції) і попередження `PlanParseFailed`.
10. **Профіль по годинах і днях тижня**. Прийнято: години й дні — в UTC (як усі дати snapshot); день тижня ISO (1 — понеділок), незалежно від DATEFIRST.
11. **Межа секції** (`partitions[].boundaryValue`). Прийнято: для RANGE LEFT — верхня межа секції, для RANGE RIGHT — нижня; дати — ISO 8601 (стиль 126). Напрям функції в snapshot не передається (див. звіт: можлива зміна контракту).
12. **Помилки збору**. Прийнято: недоступна топологія або жоден інстанс не зібрано — виняток з ErrorId `IaCollectionFailed`; `LoginRefused` у конверті — виняток `IaLoginRefused`; помилка репліки — попередження `InstanceFailed` і `collected = false`; помилка бази — `DatabaseFailed`; помилка необов'язкового набору — `DatasetFailed`, поля `null`, набір не в `collectedDatasets`.
13. **Регресія плану**. Прийнято: `hasRegression = true`, якщо у вікні ≥ 2 планів і останній за часом виконання план має avg duration щонайменше вдвічі більший за найкращий інший.
14. **Довгі тексти запитів**. Прийнято: `queryText` топ-запитів обрізається до 16 000 символів (повний текст використовується для пошуку хінтів окремим запитом).
15. **Архів**. Прийнято: час у назві ZIP — UTC; дані спершу пишуться в тимчасову підтеку каталогу архівів (успадковує обмежені права), потім стискаються; наявний каталог без обмеження прав не змінюється, лише попередження; `Remove-IaExpiredArchives` видаляє лише файли з шаблоном назви архіву (і мапу прострочених архівів) і працює навіть при `archive.enabled = false`; `Read-IaSnapshotArchive` зберігає дати рядками (`ConvertFrom-Json -DateKind String`).

## Потік 3 — Tools

1. **Дублікати назв без строгого режиму** (4.7: «невалідний файл зупиняє завантаження (строгий режим), а дублікати назв заборонені»). Прийнято: дублікат — виняток `IaToolDefinitionInvalid` завжди; `tools.strict = false` лише пропускає невалідний файл з `Write-Warning` і `Write-IaLog -Level Warning`.
2. **Звідки береться `free_query`**. Прийнято: визначення створюється в коді (параметр `@Sql`, `maxLength = limits.maxCommandLength`, Purpose `FreeQuery`), а не з Markdown; назва `free_query` у файлі — невалідна (зарезервована). `Invoke-IaTool` повторно перевіряє `unsafe.allowFreeQuery`.
3. **Перевірка SELECT під час завантаження**. Прийнято: `ConvertFrom-IaToolMarkdown` перевіряє формат і відповідність `@Name` у запиті (поза літералами й коментарями) оголошеним параметрам; `Test-IaSelectOnly`/`Test-IaSystemSourcesOnly` діють у конвеєрі Core на кожному виклику, а для вбудованих інструментів — у тестах.
4. **Необов'язковий параметр без default**. Прийнято: `Test-IaToolArguments` повертає ключ зі значенням `$null` (Core передає `DBNull`), запити використовують `(@X IS NULL OR ...)`.
5. **Порожні server/database у дозапиті**. Прийнято: порожній server → `requestedServer` (→ primary для AG); порожня база — лише якщо на інстансі зібрано одну базу, інакше `Blocked`. Зафіксовані у визначенні server/database теж мають бути в межах snapshot і резолвляться так само (ім'я AG → primary), інакше `Blocked`.
6. **Дозапит до вторинної репліки з `READ_ONLY`**. `Invoke-IaTool` (контракт) не має `-ApplicationIntent`. Прийнято: виконується без нього; помилка підключення повертається моделі в конверті. Для підтримки потрібен параметр `-ApplicationIntent` в `Invoke-IaTool` (зміна контракту).
7. **«Змінити» в діалозі**. Прийнято: змінюються лише аргументи, fetch і skip (не server/database); після успішної повторної перевірки рішення `Modified` без додаткового підтвердження; невалідна зміна не застосовується й повертає до меню; три некоректні відповіді поспіль → `Rejected`.
8. **Коли `ToolLimit`**. Прийнято: коли виконано `maxToolRequestsPerAnalysis` дозапитів, моделі надсилається вимога фінальної відповіді без дозапитів; дозапити понад ліміт — `Blocked`; `stoppedReason = ToolLimit`, лише якщо хоч один дозапит заблоковано лімітом. Якщо модель ігнорує вимогу — її дозапити `Blocked`, нового виклику немає.
9. **Ліміт токенів**. Прийнято: перед виконанням дозапитів, якщо `спожито + (вхід + вихід останнього виклику) > maxTokensPerAnalysis` (наступний виклик не менший за попередній), цикл зупиняється (`TokenLimit`), дозапити `Blocked` і SQL не виконується.
10. **Рекомендації при достроковій зупинці** (`ToolLimit`, `TokenLimit`, `BudgetExceeded`, `Error`). Прийнято: беруться з останньої успішно розібраної відповіді (розмасковані) з поясненням у `notes`; далі вони проходять перевірку 4.8 як звичайно. Відповідь, у якій `parseErrors` і немає ні рекомендацій, ні дозапитів, — `Error`.
11. **Імена колонок результатів інструментів** (5.13). Прийнято: camelCase; тексти запитів — `queryText` (для очищення літералів), імена об'єктів — `schemaName`, `tableName`, `indexName`, `moduleName`, списки колонок — рядки (`keyColumns`, `includedColumns`, `equalityColumns`, `seekColumns`...). Потоку LLM: маскування імен має покривати ці ключі. Межі секцій (`lowerBoundary`/`upperBoundary`) повертаються як є, без перетворення в UTC (це значення функції секціонування, а не час подій).
12. **Плани Query Store**. Прийнято: `query_store_plans` повертає ознаки з XML плану (індекси, scan, key lookup, missing index, неявні конверсії) через XQuery на `TRY_CONVERT(XML, ...)`; повний XML — лише з `IncludePlanXml = true`. В XQuery атрибути пишуться як `attribute::X`, щоб у літералах не було `@Name`; значення літералів предикатів не повертаються.

## Потік 4 — LLM

1. **Плейсхолдери літералів** (6, 5.13). Прийнято: `{str}`, `{num}`, `{bin}`, `{date}` (рядок, схожий на дату/час); коментарі в текстах запитів видаляються (можуть містити значення). Без ScriptDom або при помилці лексера — резервне очищення регулярними виразами (зокрема незакриті рядки).
2. **Які тексти очищуються від літералів** (5.13 «тексти T-SQL у payload»). Прийнято: тексти з сервера — `queryText`, `hintText`, `filterDefinition`, `definition`, `*_sql_text`/`statement` у результатах інструментів і XML плану (`StatementText`, `ScalarString`, `ParameterCompiledValue`, `ParameterRuntimeValue`, `ConstValue`). Скрипти програми й моделі (`executeScript`, `rollbackScript`, `functionScript`, `schemeScript`) — лише маскування імен. Межі секцій (`boundaryValue`, `boundaries`, `lowerBoundary`/`upperBoundary`) — метадані функції секціонування, не змінюються. Значення фільтра у `filterDefinition` моделі не видно.
3. **Одне ім'я в кількох категоріях** (база `Sales` і схема `Sales`). Мапа за контрактом пласка (`real -> alias`). Прийнято: один псевдонім (без урахування регістру), префікс — за першою зареєстрованою категорією; розмаскування однозначне.
4. **Імена поза переліком 5.13** (файлові групи, функції й схеми секціонування, статистики, DF/CK). Прийнято: окремо не маскуються; цілі слова, що збігаються з відомими іменами, маскуються в будь-якому тексті (крім ключів-переліків на зразок `typeDesc`, `workloadCategory`).
5. **Імена, що збігаються з типами чи функціями T-SQL** (`date`, `day`, `count(`…). Прийнято: у текстах запитів такі ідентифікатори без дужок не маскуються, щоб не зламати `CAST(... AS date)`; у структурі вони масковані.
6. **Розмаскування T-SQL моделі**. Прийнято: псевдонім-ідентифікатор замінюється справжнім ім'ям, у дужках — якщо ScriptDom не розпізнає ім'я як звичайний ідентифікатор; псевдоніми всередині імен (`IX_col3_INC`) і в рядкових літералах (`OBJECT_ID(N'sch1.tbl2')`) теж замінюються, лапки подвоюються.
7. **Бюджет** (5). Прийнято: перевірка до виклику — вже витрачене + оцінка запиту (вхід за `Measure-IaTokens`, вихід за лімітом токенів); 0 — без ліміту; пошкоджений файл обліку при заданому бюджеті блокує виклики (`IaBudgetExceeded`); в облік пишуться лише успішні виклики; записи не видаляються.
8. **`LlmResponse.error`** (5.5). Прийнято: рядок (`HTTP 429: ...`, `Таймаут: ...`), ключі й схожі на ключі фрагменти вирізано. HTTP-помилки й таймаути повертаються як `success = $false`; винятки — лише політика й конфігурація (`IaBudgetExceeded`, `IaProviderNotAllowed`, `IaSecretNotFound`, `IaConfigInvalid`).
9. **Повтори** (5). Прийнято: на 429, 5xx і таймаут; пауза 1, 2, 4… с (до 60 с) або `Retry-After`; інші помилки (400, 401) не повторюються.
10. **Параметри API**. Прийнято: OpenAI — `max_completion_tokens`; OpenAICompatible — `max_tokens`; Azure OpenAI — `api-version` за замовчуванням `2024-10-21` і `max_tokens`, з `apiVersion` ≥ `2024-12-01` — `max_completion_tokens`; Anthropic — `anthropic-version` за замовчуванням `2023-06-01`, JSON-режиму в API немає, вимога JSON додається в system. Endpoint OpenAI-сумісних — база з `/v1` або без (тоді `/v1` додається).
11. **`llm.localOnly`** (5). Прийнято: як у контракті — лише `type = OpenAICompatible` і `isLocal = true`; фактичний хост endpoint не перевіряється (локальною вважається й модель на внутрішньому сервері).
12. **Помилки секретів і конфігурації провайдера**. Прийнято: `Get-IaSecret` — будь-яка невдача (зокрема неправильний формат посилання) — `IaSecretNotFound`, значення не потрапляє в текст; відкритий ключ у `apiKeyRef` або відсутній провайдер — `IaConfigInvalid`. FullyQualifiedErrorId має вигляд `IaXxx,Функція` — перевіряти через `-like 'IaXxx*'`.
13. **Стиснення контексту** (4.3). Прийнято: payload ≤ 80 % `maxContextTokens` (решта — шаблон, схеми інструментів, дозапити); до 10 пов'язаних запитів на таблицю, до 3 планів на запит, текст запиту до 4000 символів (`queryTextTruncated`). `truncatedObjects` — `@{ objectKey; reason = Omitted|Reduced }`; `Reduced` — таблиця без нових текстів запитів, вона входить і в `includedObjectKeys`. `includedObjectKeys` — ключі таблиць та їхніх індексів (без куп).
14. **Контекст модуля Partitioning** (4.6). Прийнято: лише кандидати — таблиці зі знахідками, секціоновані або не менші за `partitioning.minSizeGb`/`minRowCount`; інші не вважаються обрізаними. Додаються секції індексів і зведення предикатів (`predicateSummary`); `drafts` модуля додає конвеєр CLI.
15. **Cross-check** (5). Прийнято: окремий виклик на кожну критичну рекомендацію; модель `llm.crossCheckProvider` без перевизначення `llm.model`; при `llm.maskNames` без мапи — `IaConfigInvalid` (немасковані імена не надсилаються); помилка виклику, нерозбірна відповідь чи вичерпаний бюджет — `verdict = Uncertain` з поясненням, конвеєр не переривається.
16. **Розташування `contracts/llm-response.schema.json`**. Схема читається з `<модуль>/contracts/` або `<репозиторій>/contracts/`. Для поставки модуля без репозиторію схему треба включити в пакет (питання оркестратору).

## Потік 5 — Rules

1. **Вікно на початку місяця** (4.4). Прийнято: `PreviousMonth` — від початку попереднього місяця (або раніше, якщо `analysisWindow.days` довше) до моменту запуску, тож вікно охоплює весь попередній місяць разом з його кінцем і перші дні поточного. Умова `AnalysisWindow` вимагає такого покриття на початку місяця і що Query Store (`firstIntervalStartUtc`) покриває вікно; без Query Store — невідомо.
2. **«Дорогий» індекс за записами** (4.4). Поріг «updates значно переважають читання» без мінімуму спрацьовував би на кожному індексі з кількома оновленнями. Прийнято: потрібні ще й `updates ≥ rules.writeOnlyMinUpdates`; без usage індекс не «дорогий». Через це write-only індекси з великою кількістю оновлень (у фікстурі й IX_Status) теж отримують пом'якшений профіль — так прямо випливає з 4.4.
3. **Пом'якшений мінімальний період і observationOverrides**. Прийнято: для «дорогих» — `min(rules.relaxed.minUptimeDays, стандартний період з урахуванням overrides)`; інтервал `minIntervalDays` не пом'якшується.
4. **Override з таблицею без бази**. Прийнято: збігається з таблицею в будь-якій базі сервера; точність: сервер < сервер+база < сервер+таблиця < сервер+база+таблиця. `Get-IaDataPeriod` враховує override до рівня бази, `Get-IaDropEligibility` — до рівня таблиці.
5. **Rebuild індексу в періоді**. Прийнято: якщо `lastRebuildUtc` індексу (на будь-якій репліці) пізніший за початок періоду, період для умови `MinUptimePeriod` рахується від rebuild (консервативно; у DataPeriod бази `lastRebuildUtc = null`).
6. **Перевірено на всіх репліках AG** (4.4). Прийнято: репліка з `collected = false` пропускається лише якщо вона вторинна з `secondaryAllowConnections = NO` (читань там бути не може); інакше умова не виконана. Репліка без бази чи без usage індексу — невідомо (`null`).
7. **Поточний аналіз і умови MinUptimePeriod/MinInterval**. Прийнято: обидві умови стосуються поточного аналізу; якщо він не зараховується, рекомендація недопустима навіть тоді, коли серія з історії вже має N аналізів.
8. **Реплікація**. Прийнято: блокує не лише `usedByReplication = true`, а й `table.isReplicated = true` (індекс опублікованої таблиці може копіюватися на підписників).
9. **Хінти в текстах Query Store**. Прийнято: окрім даних колектора й `moduleHints`, розбираються `INDEX(...)`, `INDEX = ...`, `FORCESEEK(... (...))` у текстах запитів; збіг лише за іменем індексу (без таблиці) — консервативно.
10. **Невідомі дані у перевірці DropAllowed** (4.8). Прийнято: `null` дає `Warning` (рекомендація показується), а в DropEligibility та сама умова — не виконана.
11. **ScriptDom недоступний** (4.8). Прийнято: `SyntaxValid = Failed`, перевірки за розбором (`RollbackMatches`, `PlatformLimits`, `EditionFeatures`, `PartitionAlignment`, `SafeScript`) — `Skipped`.
12. **Перекриття нового індексу** (4.8). Прийнято: ключі нового = ключам наявного або є їх лівим префіксом — `Failed`; новий індекс робить зайвим наявний неунікальний, якого немає в `replacesIndexes`, — `Warning`. Індекси з різними фільтрами не порівнюються.
13. **AlterIndex без відкату** (4.8). Прийнято: для лише `REBUILD`/`REORGANIZE` порожній відкат — `Warning`; `ALTER INDEX ... DISABLE` — `Failed` (DISABLE не використовується, 4.4).
14. **Кандидати на секціонування** (4.6). Прийнято: пороги `minSizeGb` і `minRowCount` діють разом (будь-який можна вимкнути значенням 0); частка рахується за логічними читаннями (за їх відсутності — за кількістю виконань) запитів з предикатами `Eq`/`Range`/`In`. Стовпці періоду — типи дат і цілі з назвою на Date/Day/Month/Period/Year.
15. **Межі нової функції секціонування**. Значень даних у snapshot немає. Прийнято: щомісячні межі RANGE RIGHT за останні 12 місяців і `minFuturePartitions` наперед, літерали `'yyyyMMdd'`; у плані міграції — обов'язкова звірка з MIN/MAX. Схема — `ALL TO` поточної файлової групи таблиці, `NEXT USED [PRIMARY]` для SPLIT; файлові групи за конвенцією — крок плану міграції.
16. **PK, на який посилаються FK, при секціонуванні**. Прийнято: FK тимчасово видаляються, PK перестворюється з ключем секціонування, для FK створюється окремий унікальний невирівняний індекс на старих ключах, FK відновлюються; унікальні індекси без ключа секціонування лишаються невирівняними й перелічені в `impact`.
17. **Вердикти модуля Partitioning** (5.7). Перелік вердиктів містить лише `DropRecommended|Keep`. Прийнято: для Partitioning усі об'єкти — `Keep`; історія повторів рекомендацій партиціонування береться з `Advisor.Recommendation`. `Keep.countsTowardSeries` = `isSufficient` періоду бази (на серію не впливає — Keep її обнуляє).
18. **Продуктивність на великих базах**. Похідні структури (таблиці за іменем, FK за індексом, зведення Query Store) кешуються за посиланням на об'єкт snapshot і перебудовуються, якщо змінився масив `tables`/`queryStoreQueries`; зміни вкладених полів планів після першого виклику на тому самому snapshot не підхоплюються.
19. **partitionRangeRight і межі на майбутні періоди**. Кількість повністю майбутніх секцій однакова для RANGE RIGHT і LEFT (кількість меж після моменту збору). Прийнято: тип RANGE уточнює опис у знахідці й плані; межі на кінець місяця (типово для LEFT) продовжуються кінцями місяців, час межі зберігається (`'yyyy-MM-ddTHH:mm:ss.fff'`); `null` — чернетка з `confidence = Low` і кроком перевірки `boundary_value_on_right`.

Додано індекси `IX_RunId` на дочірніх таблицях і `IX_StartedAtUtc` для каскадного видалення й очищення історії.

14. **Ключі YAML чутливі до регістру**. Прийнято: `Version` замість `version` — невідомий ключ із підказкою; значення enum порівнюються без урахування регістру й нормалізуються до канонічного.
