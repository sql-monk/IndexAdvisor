# Технічне завдання: система аналізу індексів SQL Server із використанням LLM (AI Index Advisor)

## 1. Мета

Створити систему, яка за запитом (або опційно за розкладом) збирає метадані та статистику використання індексів у робочих базах SQL Server 2019+, аналізує за допомогою LLM (хмарних або локальних) і формує обґрунтовані рекомендації щодо створення, зміни та видалення індексів. Рекомендації зберігаються в окремій базі-репозиторії. Система **не має можливості вносити будь-які зміни в цільові бази**: результат її роботи — лише рекомендації у вигляді MD-файлів і SQL-скриптів для їх втілення або HTML-звіту, що їх поєднує, які виконує DBA або розробник самостійно.

## 2. Терміни

- **Цільовий сервер** — SQL Server, індекси якого аналізуються.
- **Репозиторій** — окрема БД (IndexAdvisor), де зберігаються рекомендації та їх історія.
- **Знімок (snapshot)** — одноразовий збір метрик з цільового сервера.
- **Провайдер LLM** — OpenAI, Anthropic, Cohere, Azure OpenAI або локальна модель (Ollama, vLLM, LM Studio тощо).

## 3. Область застосування

- SQL Server 2019 і новіші версії.
- OLTP-кластери з Always On AG (збір з primary та readable secondary окремо, бо статистика використання на кожній репліці своя).
- DWH-бази до 12 ТБ, секціоновані таблиці, columnstore-індекси.
- Бази-учасники реплікації (індекси на підписниках аналізуються з урахуванням ролі).

## 4. Функціональні вимоги

### 4.1. Збір даних (Collector)

Основний режим — одноразовий запуск: збір, аналіз і рекомендації тут і зараз. Регулярний запуск за розкладом (SQL Agent, Rundeck, cron, PowerShell + dbatools) опційний і налаштовується користувачем за потреби. Під час запуску збираються:

- структура індексів: sys.indexes, sys.index\_columns, included-колонки, фільтри, компресія, секціонування, fill factor;
- використання: sys.dm\_db\_index\_usage\_stats (seeks, scans, lookups, updates, дати останнього використання);
- операційна статистика: sys.dm\_db\_index\_operational\_stats (блокування, latch, page splits);
- розмір і фрагментація: sys.dm\_db\_partition\_stats, sys.dm\_db\_index\_physical\_stats (режим LIMITED, з обмеженням за часом для великих БД);
- відсутні індекси: sys.dm\_db\_missing\_index\_details / groups / group\_stats / group\_stats\_query;
- Query Store: топ-запити за CPU/IO/тривалістю, плани, що використовують або могли б використовувати індекс;
- час останнього перезапуску інстансу (sqlserver\_start\_time) — для коректної інтерпретації обнулення DMV;
- роль репліки AG, стан реплікації, обмеження (PK, UNIQUE, FK, індекси під реплікацію, індексовані представлення).

Вимоги до колектора: мінімальне навантаження, READ UNCOMMITTED для метаданих, таймаути, можливість виключення БД/схем/таблиць, лише права VIEW SERVER STATE / VIEW DATABASE STATE, надані через роль.

**Вибір наборів даних.** Користувач сам вмикає й вимикає кожен набір із переліку вище (структура, usage stats, operational stats, розмір і фрагментація, missing index, Query Store, обмеження й реплікація) — у конфігурації або параметром CLI. Обов'язкові лише структура індексів і час запуску інстансу, без яких аналіз неможливий. У звіті видно, які набори було зібрано, і попередження, якщо вимкнений набір знижує достовірність рекомендацій (наприклад, без Query Store рекомендація на видалення лише позначає, що індекс не використовувався за такий-то період за даними DMV).

### 4.2. Репозиторій (історія рекомендацій)

- Репозиторій зберігає **лише результати аналізу**: рекомендації LLM, обґрунтування, T-SQL виконання, скрипт відкату, модель, кількість токенів і вартість, а також період роботи сервера, за який була статистика.
- Сирі дані DMV і Query Store **не зберігаються в базі-репозиторії**: колектор збирає потрібну статистику, передає її моделі й зберігає лише в локальному ZIP-архіві .
- Зібрані дані зберігаються **локально у файлах** (один ZIP-архів на запуск через вбудований Compress-Archive; в архіві — зібрані дані в JSON і повний промпт, який програма надсилає моделі, разом із версією шаблону промпту; промпт і дані зберігаються саме в тому вигляді, в якому йдуть у модель, тобто вже з маскуванням імен і літералів, якщо воно увімкнене; в архіві позначено, чи застосовано маскування, а якщо ні, програма попереджає, що архів містить немасковані тексти запитів і структуру баз і його не можна передавати в зовнішні сервіси без перевірки), щоб повторно передати їх на аналіз, наприклад іншій моделі, без нового збору з сервера. Каталог і термін зберігання налаштовуються; доступ до каталогу обмежено правами NTFS, бо файли містять тексти запитів і структуру баз. Збереження можна вимкнути.
- Для кожного індексу ведеться історія рекомендацій між запусками аналізу: саме на ній ґрунтується рішення про видалення (розділ 4.4).
- Термін зберігання історії рекомендацій налаштовується.

### 4.3. Аналіз (Analyzer)

Дворівневий:

1. **Детермінований попередній аналіз (rules engine)** — без LLM: дублікати та перекриття індексів, невикористовувані, «write-only» індекси, кандидати з missing index DMV, надмірна кількість індексів на таблиці, фрагментація.
2. **LLM-аналіз** — отримує стиснений контекст (структуру таблиці, індекси, поточну статистику, топ-запити Query Store) і формує рекомендації з поясненням, ризиками та готовим T-SQL.

LLM не має прямого доступу до цільових серверів. Вона отримує контекст від колектора і за потреби може попросити додаткові дані; після підтвердження користувача програма отримує їх через вбудовані read-only інструменти (розділ 4.7) з усіма обмеженнями й додає до контексту моделі.

**Період даних.** Кожен звіт і кожна рекомендація обов'язково показують, за який період роботи сервера зібрано статистику: час останнього перезапуску, failover і rebuild, а також період даних у Query Store. Якщо період коротший за мінімальний, користувач отримує явне попередження, а аналіз не зараховується до серії рекомендацій на видалення.

### 4.3.1. Аналіз навантаження через Query Store

Система будує профіль навантаження кожної бази: які запити виконуються, як часто, з якою вартістю і через які індекси. Це головне джерело для рекомендацій, особливо для DWH.

- Топ-запити за CPU, logical reads, тривалістю і кількістю виконань, окремо по годинах і днях тижня.
- Розбір планів виконання: які індекси використовує кожен запит (seek, scan, lookup), missing index у планах, key lookup, неявні конверсії.
- Прив'язка запитів до таблиць та індексів: для кожного індексу видно, які запити від нього залежать.
- Регресії планів і запити з кількома планами.
- Для DWH: окремо ETL-вікна (SSIS, завантаження), звітні та ad-hoc аналітичні запити; перевірка partition elimination, batch mode і segment elimination у columnstore; запити, що читають усю таблицю.
- Перед рекомендацією на видалення індексу система перевіряє, що його не використовує жоден план у Query Store за весь період спостереження.
- Дані Query Store зберігаються в самій базі, тому переживають перезапуск сервера: це доповнює DMV, які після перезапуску обнуляються.
- Система перевіряє налаштування Query Store (увімкнено, не READ\_ONLY, достатній розмір і термін зберігання) і попереджає, якщо даних не вистачає для аналізу.
- Тексти запитів перед відправкою в LLM очищуються від літералів (розділ 6).

### 4.4. Правила безпечного видалення індексу

Видалення індексу вважається рекомендованим, тільки якщо виконано **всі** умови:

- модель рекомендувала видалити індекс у N аналізах поспіль (N налаштовується, за замовчуванням 3); якщо в серії хоч раз видалення не рекомендовано, лічильник обнуляється; до серії зараховуються лише аналізи, розділені мінімальним інтервалом (налаштовується), щоб кожен ґрунтувався на нових даних, а не на тому самому вікні Query Store;
- кожен аналіз серії ґрунтувався на статистиці щонайменше за мінімальний період роботи сервера (налаштовується, мінімум 14 днів); аналізи з коротшим періодом не зараховуються;
- якщо аналіз запускається на початку місяця, вікном аналізу береться весь попередній місяць (відповідно до терміну зберігання Query Store); вікно охоплює кінець місяця;
- індекс не є PK, UNIQUE, не підтримує FK, не використовується реплікацією, не згадується в хінтах коду (пошук у sys.sql\_modules та Query Store);
- перевірено на всіх репліках AG.

**Пом'якшені вимоги для «дорогих» індексів.** Якщо індекс створює помітне навантаження — часті блокування чи очікування на ньому (row/page lock waits, latch, дедлоки з sys.dm\_db\_index\_operational\_stats), великі витрати на вставку й оновлення (updates значно переважають seeks + scans + lookups), — а читань із нього мало, вимоги до видалення знижуються: N за замовчуванням 1 замість 3, коротший мінімальний період. Пороги «дорогого» індексу та пом'якшені значення налаштовуються. У рекомендації вказано, що застосовано пом'якшені правила й чому. Структурні умови (PK, UNIQUE, FK, реплікація, хінти, репліки AG) не пом'якшуються.

**Рекомендації без очікування.** Аналіз можна запустити будь-коли й одразу отримати рекомендації, зокрема на видалення. Поки умови вище не виконано, рекомендація видається з явним попередженням: на скількох аналізах вона ґрунтується, за який період роботи сервера зібрано дані і скільки підтверджень бракує до виконання умов вище.

Етап DISABLE не використовується: щоб увімкнути вимкнений індекс, його все одно треба перебудувати, тож це те саме, що створити його заново. Перед видаленням система зберігає повний скрипт створення індексу для відкату. Період спостереження налаштовується окремо для сервера, бази й таблиці.

### 4.5. Рекомендації на створення

- Злиття схожих рекомендацій missing index, а не створення кожної окремо.
- Оцінка впливу на запис (кількість updates на таблицю), розмір, час побудови.
- Для Enterprise — ONLINE = ON, RESUMABLE = ON; для DWH — урахування columnstore та секціонування.

### 4.6. Модуль рекомендацій щодо партиціонування

Окремий модуль, який запускається незалежно від аналізу індексів. На основі Query Store, структури таблиць та індексів він визначає, чи варто партиціонувати таблицю або змінити наявну схему партиціонування.

- Кандидати: великі таблиці (поріг розміру та кількості рядків налаштовується), де запити здебільшого фільтрують за одним стовпцем дати чи періоду.
- Аналіз предикатів у запитах Query Store: які стовпці і діапазони фільтрують найчастіше, чи буде partition elimination.
- Для вже секціонованих таблиць: чи працює partition elimination, перекіс розміру секцій, порожні або переповнені секції, межі функції секціонування для майбутніх періодів.
- Обов'язкова оцінка наслідків: перебудова кластерного індексу, вирівнювання некластерних індексів, вимога включати ключ секціонування в PK та UNIQUE, вплив на FK, реплікацію та запити без фільтра за ключем.
- Окрема оцінка вигоди з обслуговування: sliding window (SWITCH, TRUNCATE ... WITH PARTITIONS), архівування, rebuild та статистика по секціях.
- Результат: рекомендація з обґрунтуванням, запропонованою функцією і схемою секціонування, планом міграції та оцінкою ризиків. Модуль нічого не виконує автоматично.
- Рекомендації зберігаються в репозиторії так само, як і рекомендації щодо індексів, разом з історією повторів.

### 4.7. Вбудовані інструменти для дозапитів моделі

Це не окремий модуль, а набір read-only інструментів усередині програми. Модель нічого не викликає сама: у відповіді вона може вказати, яких даних їй бракує (структурований запит: який інструмент і з якими параметрами). Програма показує цей запит користувачу, і лише після його підтвердження виконує запити до цільової бази та передає результат моделі як додатковий контекст для наступного кроку аналізу. Користувач може підтвердити, змінити або відхилити кожен запит; режим автопідтвердження вмикається окремим прапорцем. Інструменти не залежать від сторонніх об'єктів у цільовій базі й працюють на будь-якій базі SQL Server 2019+.

**Єдиний конвеєр виконання.** Усі запити, і колектора, і дозапити моделі, проходять через один клас доступу до SQL Server, який:

- перевіряє аргументи до підключення: сервер і база задані, довжина тексту команди не більша за ліміт (за замовчуванням 10 000 символів, налаштовується), Fetch не від'ємний;
- будує рядок підключення: Windows-автентифікація або SQL-логін, пароль лише зі змінної середовища чи захищеного сховища, параметри Encrypt і TrustServerCertificate, Application Name; ApplicationIntent за замовчуванням не задається, бо статистику треба збирати з кожної репліки AG окремо — і з primary, і з secondary, підключаючись до кожної напряму; користувач вказує лише ім'я інстансу або listener, а програма одним запитом сама визначає топологію (standalone, FCI чи Always On AG; SERVERPROPERTY('IsHadrEnabled'), sys.availability\_replicas, sys.dm\_hadr\_availability\_replica\_states) ; для Always On AG програма далі підключається до кожної репліки напряму, для standalone і FCI працює з одним вказаним інстансом;
- додає до кожного батча префікс сесії (нижче);
- обмежує кількість рядків: DefaultFetch 300, жорстка межа MaxRows 5000; якщо запитано понад 1000 рядків (поріг налаштовується), програма попереджає про великий обсяг контексту та вартість токенів; якщо результат обрізано, повертається прапорець truncated; ліміт реалізується вставкою TOP (n) після SELECT верхнього рівня або OFFSET … FETCH NEXT, якщо задано Skip;
- прив'язує значення лише через іменовані параметри @Name, які передаються драйверу як позиційні; склеювання значень у текст запиту заборонене, а невідомий параметр — помилка;
- нормалізує результат у JSON: decimal → рядок, дати → ISO 8601, uniqueidentifier → рядок, двійкові дані → base64;
- повертає однаковий конверт відповіді: success, requestId, server, database, durationMs, rowCount, truncated, columns, rows, messages, error;
- закриває підключення після кожного виклику.

**Декларативні інструменти.** Кожен інструмент описується окремим Markdown-файлом: назва, опис, метод, необов'язково зафіксовані сервер і база, типізовані параметри (рядок вигляду `- @Name: тип - опис`) і фіксований текст запиту. З файлу автоматично будується JSON-схема для моделі з additionalProperties = false. Під час виклику перевіряються типи, обов'язковість, Enum, Min, Max і MaxLength; невідомі аргументи відхиляються. Невалідний файл зупиняє завантаження (строгий режим), а дублікати назв заборонені. Набір інструментів: структура таблиць та індексів, usage та operational stats, missing index, Query Store (топ-запити, плани, предикати), розмір і секції.

**Обмеження доступу.**

- Тільки читання: команда має бути рівно однією інструкцією SELECT (перевіряється розбором через ScriptDom); друга інструкція в батчі, DDL, DML, EXEC, SELECT INTO блокуються.
- Вільний запит від моделі за замовчуванням вимкнений: модель може просити лише дані з декларативних інструментів.
- Джерела — лише системні каталоги, DMV і Query Store, без користувацьких таблиць із даними.
- Окремий обліковий запис із правами лише на метадані (VIEW DATABASE STATE, VIEW DEFINITION), надані через роль.

**Параметри сесії**, щоб дозапити мінімально впливали на роботу сервера:

- SET TRANSACTION ISOLATION LEVEL READ UNCOMMITTED;
- SET LOCK\_TIMEOUT 1000 (налаштовується);
- SET DEADLOCK\_PRIORITY LOW — у разі дедлоку жертвою стає запит системи;
- таймаут виконання команди 30 секунд і таймаут підключення 15 секунд (налаштовуються);
- OPTION (MAXDOP 1) у кожному запиті;
- ліміт кількості дозапитів і токенів на один аналіз.

**Журнал.** Кожен виклик записується в локальний Markdown-журнал, окремий файл на сесію: час початку й завершення, тривалість, сервер, база, Fetch, Skip, кількість рядків, успіх, параметри, повний текст запиту й помилка. Значення параметрів, назви яких містять password, pwd, secret, token, key, api\_key чи connection\_string, маскуються.

**Небезпечні режими.** Будь-яке з обмежень вище (перевірку на одну інструкцію SELECT, MAXDOP 1, таймаут, заборону вільного запиту) можна вимкнути окремим явним прапорцем у конфігурації або CLI. Тоді система показує попередження про ризик і записує це в журнал і в кожну рекомендацію. Перевірка на одну інструкцію SELECT діє навіть тоді, коли вільний запит увімкнено.

### 4.8. Автоматична перевірка відповідей моделі

Кожна рекомендація моделі перед показом користувачу проходить детерміновану перевірку правилами. Рекомендація, що не пройшла перевірку, відкидається або позначається як помилкова з причиною.

- Об'єкти існують: таблиця, колонки, індекс, що видаляється.
- Новий індекс не дублює і не перекриває наявний.
- Індекс, що видаляється, не є PK чи UNIQUE, не підтримує FK, не використовується реплікацією і не згадується в хінтах (див. 4.4).
- Синтаксис T-SQL коректний (локально через ScriptDom або на сервері через SET PARSEONLY ON), а скрипт відкату відповідає скрипту виконання.
- Обмеження платформи враховано: ліміти ключа та кількості колонок, редакція (ONLINE, RESUMABLE), секціонування й вирівнювання.
- Результат перевірки зберігається в репозиторії разом із рекомендацією.

## 5. Підтримка LLM-провайдерів

- Абстрактний шар провайдерів з однаковим інтерфейсом.
- Підтримка: OpenAI, Anthropic, Cohere, Azure OpenAI, локальні моделі через OpenAI-сумісний API (Ollama, vLLM, LM Studio).
- Налаштування для кожного провайдера: endpoint, модель, API-ключ, ліміт токенів на запит, денний/місячний бюджет, таймаут, кількість повторів.
- API-ключі зберігаються в захищеному сховищі (Windows Credential Manager, Azure Key Vault, HashiCorp Vault або SecretManagement у PowerShell), **не** в конфігурації відкритим текстом.
- Облік токенів і вартості для кожного запиту.
- Можливість порівняння відповідей двох моделей (cross-check) для критичних рекомендацій.
- Режим «тільки локальна модель» для баз з чутливими даними.

## 6. Безпека та відповідність&#32;

- В LLM передаються **лише метадані**: імена об'єктів, статистика, тексти запитів — без значень даних.
- Опційна маскування/хешування імен об'єктів і літералів у текстах запитів перед відправкою в зовнішні сервіси.
- Програма працює лише під обліковим записом, що має тільки права читання метаданих; облікового запису чи режиму для виконання змін немає
- Повний аудит: хто, коли й з якими параметрами запускав аналіз і які рекомендації отримав.

**Скрипт підготовки облікового запису.** До складу поставки входить окремий ідемпотентний T-SQL-скрипт (і обгортка PowerShell для запуску на кількох серверах), який створює на цільовому сервері SQL-логін, під яким програма працює за замовчуванням. Логін має мінімально необхідні права: читати метадані й статистику, але не дані й нічого не змінювати.

- Права надаються лише через ролі: серверну роль користувача з VIEW SERVER STATE і VIEW ANY DEFINITION, а в кожній цільовій базі — користувача й роль бази з VIEW DATABASE STATE і VIEW DEFINITION; перевірка існування ролі в базі — IF USER\_ID('db\_rolename') IS NULL CREATE ROLE.
- Жодних прямих GRANT логіну чи користувачу, жодного членства в db\_datareader, db\_owner, sysadmin та інших ролях із доступом до даних; SELECT на користувацькі таблиці не надається.
- Пароль генерується скриптом, відповідає політиці складності (CHECK\_POLICY = ON) і одразу зберігається в захищеному сховищі, звідки його читає програма.
- Скрипт підтримує додавання нових баз і повне видалення облікового запису, а також режим перевірки, який показує фактичні права логіну й попереджає про зайві.
- Можна використати Windows-обліковий запис замість SQL-логіну; права надаються так само, через ролі.

**Підключення лише під штатним логіном.** За замовчуванням програма підключається тільки під логіном, створеним цим скриптом (ім'я задається в конфігурації). Якщо вказано інший логін або поточний Windows-обліковий запис, програма відмовляється підключатися й пояснює причину. Щоб працювати під іншим логіном, треба явно ввімкнути окремий прапорець у конфігурації або CLI. Тоді програма перевіряє фактичні права цього логіну (зокрема членство в sysadmin, db\_owner, db\_datareader і права на зміну даних), показує попередження з переліком зайвих прав і записує це в журнал.

## 7. Інтерфейси

**CLI — основний інтерфейс.** Один запуск команди виконує збір, аналіз і видає рекомендації.

- Параметри: сервер або список серверів, бази, схеми й таблиці (включення та виключення), модуль (індекси, партиціонування або обидва), провайдер і модель LLM, вікно аналізу.
- Результат: MD-файл із рекомендаціями та обґрунтуванням і SQL-скрипти для їх втілення разом зі скриптами відкату, або HTML-звіт, що поєднує все це у зручному для читання вигляді; додатково — вивід у консоль і JSON.
- Режим без запису в репозиторій для разового аналізу.
- Коди повернення та неінтерактивний режим, щоб запускати з SQL Agent, Rundeck або cron.
- Реалізація: модуль PowerShell 7 (dbatools, SecretManagement); виклики LLM через REST (Invoke-RestMethod).

**Конфігурація з YAML.** Усі параметри CLI можна задати у YAML-файлі й передати лише шлях до нього (наприклад, -Config run.yaml). Параметри командного рядка мають пріоритет над значеннями з файлу. Файл перевіряється за схемою до запуску: невідомі ключі й неправильні типи — помилка з номером рядка. Секрети (паролі, API-ключі) у YAML не зберігаються, лише посилання на них у захищеному сховищі. Програма вміє згенерувати шаблон YAML з усіма параметрами, значеннями за замовчуванням і коментарями.

## 8. Нефункціональні вимоги

- Стек: SQL Server (T-SQL), PowerShell 7, dbatools.
- Налаштування — у YAML-файлі (розбір через модуль powershell-yaml), а не захардкоджені; репозиторій зберігає лише історію рекомендацій.

## 9. Етапи реалізації

1. Репозиторій рекомендацій і колектор.
2. Rules engine.
3. Інтеграція LLM, шар провайдерів, облік токенів.

## 10. Критерії приймання

- Програма не вносить жодних змін у цільові бази; результат — лише MD-файли з рекомендаціями та SQL-скрипти або HTML-звіт, який поєднує рекомендації, обґрунтування й SQL-скрипти у зручному для читання вигляді. Рекомендація на видалення позначає, які умови розділу 4.4 виконано, а яких бракує.
- Кожен звіт показує період роботи сервера, за який зібрано статистику.
- Перемикання між провайдерами LLM без зміни коду.
- Кожна рекомендація має обґрунтування, оцінку ризику, скрипт виконання та скрипт відкату.
